# Anti AI-Slop (Code Consistency & Cleanliness)

**Status:** ACCEPTED_TRUTH — mandatory for all agent coding in this repo  
**Goal:** Keep the template **consistent, readable, and small**. Prefer the existing house style over “impressive” AI verbosity.

Agents must treat this as a hard gate: a change that works but is sloppy is **not done**.

---

## 1. Match the house style first

1. **Read neighboring code** before writing (same package, sibling features `item` / `note` / `user`).
2. Copy **local patterns**: package layout, naming, error types, test style, DTO style (records), logging.
3. Prefer **extending** existing helpers (`common.paging`, `common.include`, `common.select`, `common.error`) over inventing parallel utilities.
4. **Do not** introduce a second way to do the same thing (two paging styles, two error formats, two mappers).

---

## 2. Smallest complete change

1. Implement **only** what the task requires — no “while I’m here” rewrites.
2. **No drive-by refactors**: renames, reformat-only diffs, package moves, dependency upgrades unless asked or required to compile.
3. **No speculative features**: no “future-proof” layers, unused interfaces, or empty TODOs for imaginary product domains.
4. Prefer **one vertical slice** (controller → service → repo) matching `feature.*` conventions.

---

## 3. No comment / doc noise

1. **Do not** add comments that restate the code (`// get user by id`, `// return response`).
2. **Do not** add AI banners: “Generated by…”, “IMPORTANT:”, decorative separators, emoji in code.
3. Comments only when they explain **non-obvious** intent, invariants, security, or a workaround with a reason.
4. **Do not** flood Javadoc on every private method; public API types may have short, accurate docs when useful.
5. Prefer clear names over long prose comments.

---

## 4. No abstraction theater

1. **No** factory/strategy/abstract base for a single implementation.
2. **No** “Utils” / “Helper” / “Manager” god classes — put logic in the feature service or a focused `common.*` type with a real job.
3. **No** premature generics/frameworks for one call site.
4. **No** wrapping Spring or JDK APIs just to look enterprise.
5. Extract a shared type only when **2+ real call sites** need the same behavior (or the template already has that extension point).

---

## 5. Clean Java / Spring habits

1. Follow existing layers: Controller (HTTP) → Service (rules/tx) → Repository (data). Controllers stay thin.
2. Reuse `ProblemDetail` / existing exceptions (`ResourceNotFoundException`, `ConflictException`) — don’t invent ad-hoc error JSON.
3. Prefer **records** for DTOs like the rest of the template; MapStruct where already used for that feature.
4. **No** `ddl-auto=update`; schema via Flyway only.
5. **No** catching `Exception` and swallowing; don’t log-and-ignore without reason.
6. Avoid null-heavy APIs; use existing validation annotations and clear 400s.
7. Keep methods short and boring; deep nesting = rewrite.

---

## 6. Dependencies & files

1. **Do not** add libraries for a few lines of code (e.g. new HTTP client, new mapper, new utils jar).
2. **Do not** add config files, wrappers, or “architecture” folders without need.
3. **Do not** commit secrets, local noise, or generated junk.
4. New files only when a clear responsibility doesn’t fit an existing class.

---

## 7. Tests without theater

1. Assert real outcomes (status, body, side effects) — not only “context loads.”
2. Meet testing policy minima; **don’t** pad with trivial tests that assert nothing useful.
3. Don’t invent mock-heavy unit tests when the suite style is MockMvc + `@SpringBootTest` for that feature.
4. Name tests after behavior: `listItems_includeCountOnly_returnsOnlyCount`.

---

## 8. Naming & formatting

1. Names match existing vocabulary (`feature`, `PageQuery`, `include`, not random synonyms).
2. Spotless owns formatting — don’t hand-format wars; run `.\mvnw.cmd spotless:apply` when needed.
3. No emoji, no marketing language in identifiers or logs.

---

## 9. Self-check before handoff (slop scan)

Agent must confirm:

- [ ] Diff is limited to the task (no unrelated files)
- [ ] Matches `feature.item` / `feature.note` style where applicable
- [ ] No redundant comments or AI banners
- [ ] No unused imports, dead code, or empty stubs
- [ ] No parallel abstraction next to an existing common helper
- [ ] Errors use existing ProblemDetail path
- [ ] Tests are meaningful and minima met
- [ ] WWG + docs updated if truth/contract changed

**Fail handoff** if the scan fails even when tests pass.

---

## 10. Examples

| Slop | Prefer |
|------|--------|
| New `ItemPaginationService` + `ItemPaginationFactory` | `PagedReads` + existing `PageQuery` |
| Comment on every line of a 5-line method | No comments; clear method name |
| Custom `{ "error": "..." }` JSON | `ProblemDetail` via `ApiExceptionHandler` |
| “Universal” base controller hierarchy | Flat feature controllers like today |
| Refactor all features while fixing one bug | Fix the bug only |
| Add Guava/Apache Commons for `isBlank` | Existing JDK / Spring utilities |
